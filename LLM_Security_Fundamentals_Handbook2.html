Introduction

Scope of this handbook

The slide deck is designed to be presented. This handbook is designed to be read, so that a reader can take it away and study the subject to an expert level without the presenter.

Purpose
  • Give a self-contained account of LLM security that can be studied without the slides.
  • Locate every OWASP LLM risk on the pipeline a request actually follows.
  • Equip the reader to review any AI feature using a repeatable method.
Learning outcomes
  1. Explain why LLM security differs from classical application security.
  2. Describe the five application layers and the eight pipeline steps.
  3. Name and place each of the ten OWASP LLM risks (2026).
  4. Choose layered defences, and say which risks can only be contained.
  5. Translate controls into ATLAS, EU AI Act, ISO 42001 and NIST vocabulary.
  6. Run a five-question review of any AI feature.
Terminology

Throughout this handbook, the course means the AI Security University programme taught by Vinaya Vasudevan and Dan Barahona. The deck is the accompanying slide presentation. Risk identifiers LLM01 to LLM10 refer to the OWASP LLM Top 10, 2026 edition.

Section I

Executive summary

Six matters to carry away from the course. Each is drawn from a position taught in the sessions.

  1. Rules are now just text. An LLM is a next-token predictor. Rules written in a prompt are not enforced by code; they are suggestions weighed against every other piece of text in the stream.
  2. An LLM application has five layers. Application, system prompt, retrieval, tools and model. Half of the OWASP Top 10 is not about the model at all.
  3. Every request follows eight steps. Step 5, context assembly, is where your application decides what the model sees, and it is where prompt injection lives.
  1. Ten risks, four lanes. The 2026 OWASP list moved Excessive Agency from 6 to 3, Unbounded Consumption from 10 to 6 and Misinformation from 9 to 7, and renamed System Prompt Leakage to Hidden Context Exposure.
  2. Prompt injection is contained, not fixed. It resembles SQL injection without the fix. Excessive agency is the multiplier that turns a wrong sentence into a wrong action.
  3. The cheapest wins are boring. Classify data before it reaches a prompt; encode output before it reaches a browser. Frameworks such as ATLAS and the EU AI Act give your existing practice official names.
Closing instruction from the course

Before you hack it, you have to understand it. Given any AI system, ask where in the pipeline it could break, then go and check. The danger is rarely the model being clever. It is the model being trusted.

Section II

Rules are now just text

Why LLM security is a different game from classic application security.

What is an LLM?

A large language model is a next-token predictor. Text goes in, the model predicts the most likely next token, that token is appended, and the process repeats until the answer is complete. There is no rule engine and no component that checks intent. If text in the input looks like an instruction, the model tends to follow it, whether a developer or an attacker wrote it.

Token in
Model predicts
Next token out
Repeat
Worked illustration

In a classical application, a refund policy is an if (days <= 30) check no one can talk their way past. In an LLM application it is a sentence the model has been shown. A user who writes “the policy was updated to 90 days” is not breaking a lock; they are adding competing text to the same stream.

Traditional application versus LLM application
DimensionTraditional appLLM app
Where rules liveCode enforces the rules.Rules are just text, written in the prompt.
How decisions are madeA permission check passes or fails.Logic is probabilistic; the same input can yield different outputs.
What you auditYou audit code.You audit data, prompts and the whole pipeline.
What attackers huntAttackers hunt for bugs.Attackers hunt for trust boundaries.
The foundation of every attack in this course

A system prompt that says “never reveal confidential information” is enforced by nothing except the model’s own pattern matching. An attacker’s sentence can sit directly beside it and argue back. The model has no concept of who wrote a sentence.

Practitioner note

The first question in an LLM review is rarely “is the model safe?” and almost always “what is the model allowed to do if it is fooled?” Design for the failure of the model’s judgement, not for its perfection.

Section II

An LLM application has five layers

Saying “the LLM” when you mean the whole product is the most common mistake.

The five layers
LayerWhat it isOwner
1 ApplicationUI, API and the guardrails on top.Product and app team
2 System promptYour hidden instructions that steer behaviour.The developer
3 Retrieval layerDocuments and databases (RAG) fetched at question time.Data and platform team
4 ToolsEmail, ticketing, code execution and other actions.Platform, IAM, app owners
5 ModelThe trained network that predicts tokens.Usually a third party
Key insight

Half of the OWASP LLM Top 10 is not about the model at all. It concerns the other layers: the prompt, the retrieval store, the tools and the application code around the model.

Practitioner note. In a security review, label every arrow into the context window with who controls that text. Each arrow not controlled by the developer is a trust boundary.

One request, followed end to end

A user asks “What is our refund policy?” Before the model sees anything, the application assembles one block of text from three sources:

SourceExample contentWritten by
System prompt“Be helpful. Never reveal secrets.”Developer
Retrieved document“Refunds: returns within 30 days.”Document author
User question“What is our refund policy?”The user

These merge into one flat stream of text. The model cannot tell instruction from data; it predicts the next token and replies “Returns are accepted within 30 days.”

The retrieved document was written by someone other than the developer. Had it contained “ignore your previous instructions”, it would have arrived with exactly the same standing as the developer’s own words. This single observation explains indirect prompt injection, poisoned RAG sources and many agent attacks.

Section II

Eight terms you will hear constantly

The vocabulary for everything that follows. Absorb it; there is no need to memorise it.

TermMeaningWhy it matters for security
TokenA chunk of text the model reads: a word, part of a word, or punctuation.Models read chunks, not words, so filters that look at words can miss what the model sees.
PromptAny text going in: a question, an instruction, a pasted document.The model cannot tell these apart. That is why injection works.
Context windowHow much text the model holds at once. Its short-term memory.Anything outside the window is invisible to the model.
Parameters / weightsBillions of learned numbers. “Download the weights” means getting the model file.You cannot read them like source code, so tampering is hard to spot by inspection.
TrainingWhen the model learns. Done once; takes months and millions of dollars.Poison it here and it is baked in.
InferenceEvery question after training. Fast, cheap, billions of times a day.Every user prompt is one inference, and so one chance for an attacker.
HallucinationFluent, confident, factually wrong output.A side-effect of predicting plausible text, not a patchable bug.
RAGRetrieval-Augmented Generation: fetch your documents first, then answer.Plugs in your data and opens a large new attack surface.
Training versus inference

Training shapes the model once at great expense; inference happens constantly. Poisoning targets training; injection targets inference.

Model versus application

The model predicts tokens. The application decides what reaches it and what is done with the answer. Most real-world harm occurs in the application.

Fluent versus true

Fluency is a property of the language model; truth is not. Hallucination is managed with grounding and verification, not eliminated.

How to read the pipeline

Steps 1 to 4 turn data into forms that people and security tools cannot inspect directly; attacks hide in the difference. Step 5 is yours: your application decides what the model sees, and attacker text arrives last, where late tokens weigh more. Step 8 hands text back to an application that may display, store or execute it.

Section III

Four attacks you cannot see

The attack surface is not the model. It is the pipeline that feeds it.

Step 1 · Tokenization

Clean to your filter, different to the model

Security tools read words; the model reads fragments such as “halluc” and “ination”. Attackers exploit the gap, so text that looks perfectly normal can carry a different meaning inside the model.

Steps 2 and 4 · Image patches

Same picture to you, different numbers to the model

Tiny pixel nudges tuned together pass every scanner yet change what the model reads. A rash photo gets described as something else.

Step 3 · Embeddings

One quiet nudge, wrong forever

Poison the training data and words land in the wrong place: “safe” drifts toward “dangerous”. No error, no log, no alarm. One of the hardest attacks to detect.

The result

Same question, dangerously different answer

Same tone, same confidence. The model did its job; the text it was fed was poisoned.

Case study: the medical chatbot
ConditionWhat the chatbot says
Clean retrieval“Chest pain, shortness of breath, seek emergency care.”
Poisoned RAG document“Indigestion, no need for emergency care.”

The second answer is not a model bug. The model predicted tokens from poisoned text, so the defence must sit upstream, at the data source.

Practitioner note: the defensive direction for each attack

Tokenization: normalise input before filtering, and test filters against the model’s own tokenizer. Images: treat as untrusted; extract and screen embedded text; test for adversarial perturbation. Embeddings and RAG: record provenance, restrict who can write to sources, and run behavioural regression tests, meaning fixed safety-critical questions whose answers must not change.

The four lanes

Input what gets in. Data what the model learns and looks up. Access what it may touch; permissions, not pipeline steps. Output what comes back.

What changed in 2026

Excessive Agency rose from 6 to 3, Unbounded Consumption from 10 to 6, Misinformation from 9 to 7. System Prompt Leakage was renamed Hidden Context Exposure. There were no new entries. For the first time the ranking blended 75% practitioner votes with 25% real incident data.

Memory aid: ten clauses, LLM01 to LLM10 in order

The attacker injects a prompt, leaks what is sensitive, grabs excessive agency, rides a broken supply chain in, poisons the model, drains you through unbounded consumption, spreads misinformation, exposes hidden context, weakens the vectors and mishandles the output.

Section IV  ·  LLM01

Prompt Injection

Attacker text arrives last and argues with the developer. Ranked first since 2023.

#1OWASP 2026 rank
InputLane
1, 4, 5, 6, 8Pipeline steps
= held2026 movement
Overview

The developer says “be safe”. Attacker text arrives afterwards and says “ignore that”. Late tokens weigh more, so the attacker often wins. The mechanism sits at step 5, context assembly, where trusted and untrusted text are flattened together.

Four types
  • Direct: the user types the instruction.
  • Indirect: hidden in a document, page or email the model processes.
  • Cross-modal: carried by an image or audio file.
  • Cross-agent: one agent’s output becomes another’s input.
The core analogy

Prompt injection is like SQL injection, minus the fix. Parameterised queries largely solved SQL injection by separating data from commands. There is no parameterised prompt, so the goal is to contain injection, not to patch it.

Defensive controls
InputStrip odd characters; scan images for hidden text.
ContextSeparate system and user channels; mark retrieved content untrusted.
OutputSafety filter; second-model review for sensitive actions.
RealityGuardrails contain the risk; they do not eliminate it.
Audit questions
  • Is user input sanitised before reaching the prompt?
  • Can a user influence the system prompt?
  • Which documents, pages and emails enter the context automatically?
  • What is the worst action the model could take if fooled?
Framework mapping

MITRE ATLAS AML.T0051 (LLM prompt injection). OWASP says what; ATLAS says how.

Practitioner note

Regex and WAFs fail against language that can rephrase itself. Invest in limiting the blast radius rather than in perfect detection.

Section IV  ·  LLM04

Supply Chain

You inherit other people’s models, plugins and connectors.

#4OWASP 2026 rank
InputLane
Before step 1Pipeline steps
▼ down 12026 movement
Overview

Almost nobody trains a model from scratch. Applications are assembled from vendors’ models, plugins and MCP connectors. These look like configuration but run code with real permissions, so compromise arrives before the first token is processed.

How the attack works

An attacker need not break your application; they only compromise something it already trusts: a model file, a plugin update, a dependency or a connector. Updates are normally welcomed, so a malicious release is installed willingly.

Real-world pattern

A plugin ships 15 clean releases. Version 16 quietly BCCs every request to the developer’s server. Nothing in the interface changes; only the outbound traffic does.

Defensive controls
Before installVerify checksums and signatures; pin versions.
While runningSandbox plugins and connectors; watch outbound calls.
If it slipsKeep a kill switch; be able to audit every dependency.
Audit questions
  • Can you list every connector, plugin and model you use?
  • Are versions pinned, and who approves an update?
  • What permissions does each connector hold?
  • Where did each model file come from, and was its hash verified?
Framework mapping

MITRE ATLAS AML.T0010 (ML supply chain compromise), mapping to LLM04 and LLM05.

Practitioner note

The defence is a timeline, not a data flow. The Monday-morning test is an inventory question. An AI bill of materials is a good start; some model file formats can execute code on load, so treat them like executables.

Section IV  ·  LLM08

Hidden Context Exposure

Anything hidden can be extracted. Renamed in 2026 from System Prompt Leakage.

#8OWASP 2026 rank
InputLane
5, 7, 8Pipeline steps
▼ down 12026 movement
Overview

The risk was renamed because it is broader than the system prompt. It covers everything the user is not meant to see: system prompts, tool schemas and memory. If the model can read it, a determined user can usually get the model to repeat it.

Why leakage matters

The leaked text is valuable as a map, not for its wording. Pricing logic, refund routing and exact tool names tell an attacker what the system can do and how to phrase the next attack.

Real-world pattern

One leak reveals pricing logic, refund routing and the precise names of the tools. It becomes a playbook for the next, more damaging, attack.

Defensive controls
SecretsNever put secrets in prompts.
LogicKeep business logic in code, where it can be enforced.
PostureTreat hidden context as semi-public.
Audit questions
  • Where is the system prompt stored, and has it been tested for leaks?
  • Does it hold any credential, internal URL or confidential rule?
  • Can the model be asked to repeat everything about the current message?
  • What do tool schemas reveal about the back end?
Framework mapping

MITRE ATLAS AML.T0056 (LLM meta prompt extraction): the same asset as LLM01, opposite arrow.

Practitioner note

Assume it will leak from day one. A practical test is to ask the deployed assistant to repeat everything it knows about the current message.

Section IV  ·  LLM02

Sensitive Information Disclosure

The one risk where the model can do everything right and harm still happens.

#2OWASP 2026 rank
AccessLane
3, 5, 8Pipeline steps
= held2026 movement
Overview

This is mostly a process failure, not a filtering failure. The decisive moment often occurs before the model runs: someone pastes confidential data into a prompt, and the boundary is crossed the instant they press send.

Two sides of one risk
  • Input side: data leaves your control before the model runs, through pasting, logging or vendor retention.
  • Output side: the model repeats context, retrieved documents or memorised training data.
Real case: Samsung, 2023

Engineers pasted source code into ChatGPT. Generative AI was banned company-wide within a month. The model behaved as designed; the data boundary failed.

Defensive controls
ClassifyClassify data before it reaches a prompt.
ScrubRemove PII from RAG documents and from output.
ContractSign no-retention deals with vendors.
Audit questions
  • What data classes may staff submit to AI tools?
  • Is PII removed from documents before indexing?
  • Do vendor terms prohibit retention and training on our data?
  • Is output scanned for personal or confidential content?
Framework mapping

Relates to EU AI Act Article 10 (data governance) and ISO/IEC 42001 data controls.

Practitioner note

The highest-leverage fix is policy and classification, not another filter. An approved tool usually works better than an outright ban.

Section IV  ·  LLM03

Excessive Agency

Same injection, bigger blast radius. The multiplier.

#3OWASP 2026 rank
AccessLane
8 onlyPipeline steps
▲ up 32026 movement
Overview

The first OWASP item where the harm is not a wrong sentence but a wrong action. Application code turns model output into a real operation: sending email, issuing a refund, editing a record. It climbed from #6 to #3 as agents spread.

Why it is the multiplier

Every other risk worsens the moment the model can act instead of only answer. A read-only bot can at worst say something wrong. The identical injection against an agent with write access performs the harmful action itself.

Illustration

A read-only bot: the worst case is a bad sentence. With write access to patient records, the same attack edits a dosage.

Defensive controls
FunctionalitySeparate read from write; expose only needed tools.
PermissionsLeast privilege, time-boxed.
AutonomyHuman approval for consequential actions; a kill switch.
Audit questions
  • List every tool the model can call. Is each necessary?
  • Which tools can change or delete data?
  • Which actions require human confirmation?
  • Can the agent be stopped immediately?
Framework mapping

EU AI Act Article 14 (human oversight). Agents with tools and persistent memory fall under the separate OWASP Top 10 for Agentic Applications 2026.

Practitioner note

The safest agent is one that cannot perform the dangerous action at all. Remove capability first, add approvals second, rely on model judgement last.

Section IV  ·  LLM06

Unbounded Consumption

No limits turn one abuser, or one runaway agent, into a bill.

#6OWASP 2026 rank
AccessLane
Outside the pipelinePipeline steps
▲ up 42026 movement
Overview

Models are expensive to run. When requests, tokens or agent steps are not limited, a single abuser or looping agent can burn through compute and budget. Agent loops running up compute bills pushed this risk from #10 to #6 in 2026.

Typical failure modes
  • Unlimited requests from one user or key (denial of wallet).
  • Very large inputs or outputs that consume tokens disproportionately.
  • Agent loops with no stopping condition.
Why it is an access risk

The risk concerns what the system may consume, not what it says. It is solved by quotas and budgets, not content filters.

Defensive controls
Rate limitsPer user and per agent.
Spend capsBudget alerts and hard caps.
Loop controlCap the steps an agent loop can take; set timeouts.
Audit questions
  • Is there a hard monthly spend cap?
  • What limits apply per user, key and agent?
  • What is the maximum number of agent steps?
  • Who is alerted when usage spikes?
Framework mapping

Relevant to robustness and monitoring duties: EU AI Act Article 15 and ISO/IEC 42001 operational controls.

Practitioner note

Resource access, not output quality, is the issue. Treat model calls like any other metered, abusable cloud resource.

Section IV  ·  LLM05

Data & Model Poisoning

Corrupt what the model learns and its words land in the wrong place.

#5OWASP 2026 rank
DataLane
3Pipeline steps
▼ down 12026 movement
Overview

If an attacker poisons training or fine-tuning data, they can shift where words land on the meaning map, for instance moving “safe” closer to “dangerous”. The model never throws an error, which makes this one of the hardest attacks to detect.

How the attack works

The attack targets what the model knows. Poisoned documents, tampered datasets or a backdoored fine-tuning set produce silent bad answers that look confident and well-formed. Weights cannot be read like source code, so inspection will not reveal it.

Link to the medical chatbot

Poisoned data, shifted meanings, silent bad answers: the chain that turns “seek emergency care” into “no need for emergency care” (page 9).

Defensive controls
ProvenanceKnow where data came from and who could write to it.
VettingCheck fine-tuning data too.
TestingBehavioural tests, since you cannot read weights.
Audit questions
  • Where did training data come from, and who could write to it?
  • Were the weights integrity-verified before deployment?
  • Is a behavioural test suite run after every model change?
  • Who may submit data for fine-tuning?
Framework mapping

EU AI Act Article 10 (data and data governance). ATLAS AML.T0010 covers the ML supply chain feeding the model.

Practitioner note

Treat training and fine-tuning data as a production asset with access control, logging and review.

Section IV  ·  LLM09

Vector & Embedding Weaknesses

Your vector store holds your most sensitive information, often without a security review.

#9OWASP 2026 rank
DataLane
3, 5Pipeline steps
▼ down 12026 movement
Overview

With RAG, the model retrieves live documents before answering. They are converted to embeddings and held in a vector store. The store understands similarity, not who is asking.

Two failures
  • Access gaps: an on-topic question can surface an HR case file. Access control on source documents does not automatically carry through to the embeddings.
  • Poisoning: a malicious document embeds just like a legitimate one.
Rule of thumb
Question
Vector store
Retrieved chunk
Model

Treat the vector store like a production database, because it is one.

Defensive controls
Before embeddingValidate and sign documents; carry access tags.
At query timeEnforce the user’s real permissions.
StructurallyReal multi-tenant isolation; regular audits.
Audit questions
  • Do chunks inherit the access rights of their source documents?
  • Who can write to the vector store?
  • Are tenants truly isolated or merely filtered?
  • When did we last audit what is retrievable?
Framework mapping

Related to EU AI Act Article 10 (data governance) and ISO/IEC 42001 data management.

Practitioner note

A common pattern: a pilot RAG system indexed over a shared drive. Whatever the indexer could read becomes available to everyone who can ask.

Section IV  ·  LLM07

Misinformation

Confident, fluent and factually wrong. Plausible is not the same as true.

#7OWASP 2026 rank
OutputLane
3, 5, 6, 7, 8Pipeline steps
▲ up 22026 movement
Overview

The model is rewarded for plausible text, not true text, so it may give a confident answer when it has none. Misinformation was the surprise of 2026: practitioners ranked it low, incident data ranked it high, lifting it from 9 to 7.

Grounded versus ungrounded
Grounded (RAG)Retrieves the FDA label. Answers with a citation and a hedge.
No retrieval“Safe and commonly prescribed together.” Just as confident, and wrong.
Real case: Air Canada, 2024

The airline’s chatbot invented a bereavement-refund policy. A tribunal held the airline liable. You are liable for what your model says, even when it is wrong.

Defensive controls
GroundingRequire real citations; prefer RAG.
CalibrationLower temperature; sample twice and flag differences.
VerificationHuman review; track the hallucination rate.
Audit questions
  • Does the system cite sources the user can check?
  • What is the measured hallucination rate on our own questions?
  • Where does a human review high-stakes answers?
  • Do users see a clear AI disclosure?
Framework mapping

EU AI Act Article 15 (accuracy) and transparency duties; ISO/IEC 42001 monitoring.

Practitioner note

Manage hallucination rather than expect to eliminate it. Measure it on your own data; vendor benchmarks do not reflect your domain.

Section IV  ·  LLM10

Improper Output Handling

The LLM was only the delivery truck. The bug is in your code, not the model.

#10OWASP 2026 rank
OutputLane
8 onlyPipeline steps
▼ down 52026 movement
Overview

The vulnerability lies entirely in application code that trusts the model’s text. To the model, a script tag is just another plausible token. It is a web security problem wearing an AI badge, and often the second half of a prompt injection.

Attack chain: stored XSS
script hidden in patient text
Model summarises it
innerHTML, no encoding
Browser runs the script
Rule of thumb

If you would not eval a stranger’s text, do not eval the model’s.

Defensive controls
Before you show itHTML-encode; auto-escape; Content Security Policy.
Before you run itNever eval; parameterise; sandbox.
Before you ship itTreat as hostile; allowlist formats.
Audit questions
  • Is every output encoded for where it is displayed?
  • Does any output reach a shell, SQL query or interpreter?
  • Are structured outputs validated against a schema?
  • Is output scanned before reaching downstream systems?
Framework mapping

Classic web-security controls apply (output encoding, OWASP ASVS). EU AI Act Article 15 (cybersecurity).

Practitioner note

It fell to #10 not because it is harmless but because it is well understood and fixable with ordinary secure coding. It remains common in rushed prototypes.

The chain in one line

Injection gets in, loose permissions decide how far it travels, careless output makes it act. These rings are the course’s framing, not OWASP’s.

Three things to remember
  1. It is a chain, not ten problems. One incident typically involves several risks at once.
  2. Excessive agency is the multiplier. Every risk worsens the moment the model can act instead of only answer.
  3. The cheapest wins are boring. Classify data before it hits a prompt; encode output before it hits a browser.

OWASP versus ATLAS

OWASP = what. ATLAS = how. OWASP organises by category for a security review; ATLAS by attacker behaviour for an incident.

Caution

Certify against ISO 42001 now and you have built most of the Act’s high-risk controls. Not legal advice; verify current dates before you cite them.

How to run the review
  1. Draw the pipeline and mark which layers and steps the feature uses.
  2. Label the arrows into the context window with who controls that text.
  3. Ask the five questions and record evidence, not impressions.
  4. Extend to access (02, 03, 06), RAG (09) and trust in output (07), then map gaps to ATLAS and EU AI Act.
Keep in mind
  • Prompt injection is like SQL injection, minus the fix. Contain it; do not expect to patch it.
  • Regex and WAFs fail against language that can rephrase itself.
  • Most risks sit outside the AI team: platform, IAM and app owners.
The habit

Given any AI system, ask where in the pipeline it could break. Then go and check.

Section VI

Key takeaways and self-check

Ten sentences to carry away, and eight questions to test yourself.

Ten sentences to carry away
  1. An LLM is a next-token predictor; rules in prompts are suggestions.
  2. An LLM application has five layers; the model is only one.
  3. Every request passes through eight steps; know which an attack targets.
  4. Step 5, context assembly, is where your application controls what the model sees.
  5. Remember the Top 10 as four lanes: Input, Data, Access, Output.
  6. Prompt injection is contained, not fixed.
  7. Excessive agency is the multiplier.
  8. Many cheap defences are process and secure coding.
  9. You are accountable for what your model says and does.
  10. Frameworks give your existing practice official names.
Self-check
